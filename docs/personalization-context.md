# Declared company context and current viewer framing

The production company analyzer reads `GET /company-service/internal/knowledge/companies/{companyId}?asOf=...` before reasoning. Its optional `declaredProfile` contains `region`, `industrySections` (A–U, separate from numeric `industryCodes`), `revenue` (`amount` decimal string, nullable `currency`/`period`), nullable `countOfEmployees` and one exact snapshot `sourceRef`. Legacy absence stays null. A missing profile is unknown, while an unavailable service fails the analysis before save. No current operational fields are substituted for an historical `asOf`.

CompanyService explicitly captures a single company's current declarations with `POST /company-service/internal/knowledge/companies/{companyId}/capture-declared-profile`, body `{ "captureId": "opaque-stable-id" }`. Reads never capture. The snapshot is immutable Context material with `sourceId=company-operational-declared-profile`; its JSON text is `{companyId,region,industrySections,revenue,countOfEmployees}`. Agent verifies exact reference/hash, source marker, content/field equality, company and knowledge time before presenting it to reasoning. Capture time is not the company's creation time or an invented CSV import time. Existing profile revisions and documentary exposures remain separate. The CSV importer is out of scope; call capture explicitly after the operational write succeeds and before analyzing at a later `asOf`.

Region and industry declarations inform relevance, applicability explanations and questions. Registered region is not proof of every operating location: mismatch does not automatically exclude an effect. A declared profile is a profile signal, not a contract, payment, loan, budget or established financial exposure. Code excludes profile signals from literal/economic object extraction and budget evidence, and returns correctable 422 `DECLARED_PROFILE_EXPOSURE` when profile-only evidence is promoted to documentary financial exposure. Unknown amounts, currency, periods, headcount and exposure remain unknown; null never means zero.

The assistant's `assistant_company_profile` tool returns the same versioned profile and a separate `viewer`. If `USER_SERVICE_URL` is configured, the existing internal service client calls `GET /user-service/internal/users/{persistedChatOwner}/viewer-context?companyId={currentMembership}`. The UserService endpoint checks current membership and assigned-role ownership and returns only `{userId,companyId,role:{id,name,isDefault}|null,observedAt}`. Agent validates identity, strips unrelated fields and never accepts a model-provided user/company id. `viewer.status=available` with `role=null` is a known unassigned role; `status=unavailable` means missing integration or failed read. Current role `observedAt` is separate from historical company `asOf`.

Viewer role changes emphasis and recommended actions only: financiers focus on liquidity and calculation assumptions, directors on decisions, timing and responsibility. Custom titles do not establish permissions or unstated duties. Viewer context is never sent into canonical company analysis or analysis persistence; it does not change source facts, question identity, sums, periods, evidence status, category, company importance or access grants. No auth roles, assignments, ACL, public ingress, payments integration or frontend behavior changes.

Tests use existing in-process fake HTTP/provider seams. They cover region match/mismatch payloads, A–U preservation, exact decimal/null semantics, snapshot mismatch/future/scope failures, profile-only exposure guards, trusted-owner financier/director/null-role framing, unavailable role reads and DTO allowlists. These prove contract and isolation behavior without claiming to measure live model relevance quality. Run `npm test`, `npm run typecheck`, `npm run check`, `npm run test:built` with `TEST_DATABASE_URL` unset. No live provider or external database is required.
