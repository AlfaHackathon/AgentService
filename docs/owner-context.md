# Owner snapshots in news reasoning and recipient actions

This source integration is based on Agent master `8c1422dcc4f629ffd12884270307695a86f696c3`. It reads the contracts published in Company PR7/PR8, User PR6 and Context PR10. It performs no capture, CSV import, provisioning, migration or runtime enablement.

Set `NEWS_OWNER_CONTEXT_ENABLED=true` only in a coordinated rollout after the owner gates. The default is `false`, preserving the existing flow. `USER_SERVICE_URL` is an optional existing service address using the existing internal secret, not a new credential. Without it, recipient account context stays unknown. Payment activity additionally requires both `NEWS_PAYMENT_SOURCE_ID` and `NEWS_PAYMENT_SOURCE_VERSION_ID` from trusted dataset/import scope. Partial payment configuration is rejected; no source/version is guessed or selected as latest. These are identifiers, not secrets or a model-call cap.

Company reasoning reads `GET /company-service/internal/bank-profiles/{companyId}?asOf=...` and, when configured, `GET /company-service/internal/payment-activity/{companyId}?sourceId=...&sourceVersionId=...&asOf=...`. All 23 nullable BankData fields are retained, including raw codes/flags/gradations, full digital OKVED and exact revenue text. No boolean encodings, period/currency for declared revenue, employee counts or parent-company relationship are inferred. Payment amounts/counts remain strings; RUB, unknown period year/end, unknown coverage and the separate self-transfer bucket are preserved. Supplied aggregate-row counts are not evidence of cross-row transaction disjointness, annual cashflow, revenue or supplier/contract exposure.

`ReasoningInput.declaredContext` contains Company UUID/asOf, the exact bank snapshot and payment activity or nulls, and a declared-only usage policy. The native company reasoner already serializes the complete ReasoningInput; no narrative/calculation/repair files are changed. This canonical phase never requests a viewer snapshot or receives an account role.

Recipient actions start from an authoritative Insight role scope, not model arguments. Only a UUID person ID can be resolved by `GET /user-service/internal/source-accounts/by-pair?sourcePersonId=...&companyId=...&asOf=...`. The returned F/U/account identities are checked before fetching `GET /user-service/internal/users/{resolvedUserId}/viewer-context?companyId=...&asOf=...`. Person ID is never assumed to be account User ID. The model-facing source-account projection omits sourcePersonId and any PII/ACL fields. The viewer DTO remains the owner's safe allowlist.

When a captured account role exists, only the cloned action-framing profile uses its name. The original knowledge role remains labeled in recipientContext. Canonical receipts/facts/groups, opaque scopeVersion, permissions and arithmetic are untouched. Company context is cached only for one projection call; no client-lifetime cache grows across jobs. Combined company/recipient context is bounded before the role agent runs. Owner errors fail that role view through the existing error path, leaving canonical company facts intact.

404 means unknown: a missing bank/payment snapshot becomes null; a missing mapping or an unconfigured/legacy person leaves the original role profile unchanged; a missing viewer keeps viewer=null. No current operational/user read or GET-side capture supplies missing history. Authentication, malformed payload and scope/hash/time failures propagate rather than masquerade as 404. Snapshot hashes are preserved as opaque owner values, without assuming JavaScript and .NET canonical JSON bytes match. Knowledge times retain 100 ns precision and must be within the requested asOf.

Contract/economic-object catalogs exclude the explicit declared source families `company-bank-profile`, `company-operational-declared-profile`, `provided-bank-csv`, `company-payment-activity`, and `company-payment-rows`. Context reads, including follow-up tools, separate these and the configured payment source from documentary materials. Their raw text cannot create contract/economic handles or satisfy a documentary/budget source citation. Exact excluded material/version/hash/source metadata remains under `nonDocumentarySources`, with conservative incomplete coverage. Raw duplicate profile/payment tables are not copied into the prompt beside typed owner data. This is source-type enforcement, not a heuristic based on words like loan or supplier.

Each complete owner block is bounded at 48000 serialized characters, and the combined recipient block has the same limit. Required fields are never truncated to fit. The existing overall company evidence/prompt/tool budgets still apply. If Context itself rejects an upstream material budget, that failure remains visible; the Agent does not invent a partial or zero result. The payment API supplies derived scoped aggregates, not the raw large dataset.

Model-free gates: `npm test`, `npm run typecheck`, `npm run check`, and `npm run test:built` with `TEST_DATABASE_URL` unset. Tests exercise real owner HTTP clients with fake responses, fake-provider native assistant serialization, full field/precision/null retention, 404 compatibility, source/time/hash isolation, declared-material guards and financier/director framing with invariant canonical facts. No live LLM, real CSV, server deployment or external DB is needed.
