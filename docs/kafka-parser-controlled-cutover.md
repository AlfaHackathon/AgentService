## Why a normal enable is not a one-message test

- `NEWS_KAFKA_FROM_BEGINNING` defaults to `true`. KafkaJS first uses valid committed group offsets; the flag selects the start position only for partitions without a valid committed offset. Setting it to `false` does not skip the existing group's backlog. A fresh group with `false` intentionally excludes its earlier records, which must be an explicit owner decision.
- The consumer has no message-count limit or ID allowlist. `partitionsConsumedConcurrently=1` serializes work, not total admissions. Several records can be processed before an operator reacts to the first success log. Polling status and stopping after one ack is not a reliable one-message bound.
- `NEWS_KAFKA_ENABLED=false` disables only Kafka ingress. Composition starts `NewsFlow` and `SourceChangePump` independently, and `NewsFlow.enqueue` starts the worker after a durable job is created. Existing jobs/source changes can execute without any Kafka message.
- One admitted news job can run several model phases and select multiple companies (default company budget 12). The strict `{Source,Id}` envelope cannot carry company/user routing fields. Do not weaken it or invent a company override to make a canary look scoped.

## Safe single-record transport canary on the existing stack

1. Root first resolves the core/schema gate and the independent company-final fix. Keep production-topic Kafka consumption disabled. Record existing non-secret config identities and read-only broker metadata: production topic/partitions, group identity, committed offsets, log-start/end offsets and lag. Do not change offsets or group membership to obtain this snapshot.
2. Use an operator-confirmed isolated canary topic on the **existing** broker and a distinct, explicit canary group. This does not require a new DB or environment. The topic must have no other writers and exactly one approved synthetic `{Source,Id}` record across all partitions for this trial. If it does not exist, creating it/publishing the record is a separate explicit root action; this patch never does so automatically. Production group/topic offsets remain unchanged.
3. Before any admission, root must establish the allowed job/company/model scope and inspect existing durable job/source-change backlog. If unrelated workers or pending work make the requested budget unbounded, do not call this an isolated full-flow test. Stop at parser read/source-contract evidence and the local admission fixture until a coordinated existing-worker window is available. No new process claiming global jobs should be started merely to test the ID reader.
4. Confirm the selected synthetic document's parser read is stable for the trial; retain its returned publisher ID/content identity as approved evidence. A mutable Mongo document is not an immutable publisher snapshot. Do not replay real historical financial data as a synthetic fixture.
5. Only the release owner may configure the canary topic/group and enable its consumer after confirming the topic contains just that one record. With a fresh canary group, `FROM_BEGINNING=true` is safe only because that explicitly inspected canary log contains exactly the approved record. Do not use the production group or silently alter the production starting position.
6. Observe the existing internal `GET /agent-service/internal/news-analysis/kafka`: `lastAccepted` gives topic/partition/offset/jobId. Independently verify the exact Context material/version and durable Insight job. Confirm committed offset is exactly the admitted record's offset plus one; source rejection, transient exhaustion, heartbeat loss, stale batch or uncertain job save must not be treated as an ack. Job/analysis completion is a separate check from admission.
7. Stop the canary consumer through normal coordinated shutdown, restore the captured configuration, and confirm the production Kafka consumer remains disabled and its offsets unchanged. Retain the canary record/group for audit; do not delete/reset/skip records as cleanup. A stable replay can reuse the same Context/job identity; changed Mongo content may legitimately admit a different observed version.

If an isolated canary topic or a bounded worker window is unavailable, the present consumer cannot guarantee a one-record production-topic test. Report that blocker; do not approximate it with a fast stop, automatic seek or an unannounced fresh production group.

## Production backlog is a separate decision

An existing production group should resume its committed offsets only after root approves its backlog scope and processing/model budget. This candidate has no bounded-drain control. A fresh group starting at latest leaves the older range unconsumed by that group and is not a backlog migration. An explicit offset move/seek/reset is also a separate data-processing decision requiring the exact excluded topic/partition ranges and approval. None is performed or recommended as an implicit prerequisite of enabling this adapter. Poison records remain unacked and pause the partition; repair source/configuration and recover deliberately.

## Gates and rollback

Run `npm run typecheck`, `npm run check`, `env -u TEST_DATABASE_URL npm test`, and `env -u TEST_DATABASE_URL npm run test:built` in the existing coding workspace. The built gate includes production build. Focused transport gate: `npx vitest run tests/news-kafka-consumer.test.ts tests/news-parser-reference.test.ts tests/news-parser-admission.test.ts`. Never run `test:live` for source validation.

Deploy the approved combined Agent tree with `NEWS_KAFKA_ENABLED=false` first; preserve existing `NEWS_SERVICE_URL` (base includes `/news-parser-service`), `INTERNAL_SECRET` and broker configuration without copying their values into reports. No adapter migration, parser edit, frontend edit, new port or ACL change is required. The existing internal credential is reused; the URL is an address, not a credential. Enabling consumption and any model execution remain separate owner actions after runtime compatibility evidence.

On failure, disable the consumer before coordinated rollback and preserve committed offsets and durable jobs. An older binary cannot decode two-field references, so re-enabling it would block without ack. Disabling Kafka does not cancel an already admitted job or stop the general job/source-change workers; coordinate those through existing lifecycle controls. Do not erase queued work or claim that rollback reverses admission.
