# Правила новостного анализа

CompanyService выполняет выбор компаний и сегментов, InsightService — идентичность вопросов,
решения глубины, применимость, расчёты, приоритеты и ролевой допуск. AgentService вызывает эти API;
описанные ниже ограничения модели, цитат, бюджетов и полноты её ответа применяются в Flue runtime.

## Уточнения текущей версии: учёт отдельных сигналов

Публичные источники теперь проходят отдельные extraction/review до сегментных выводов. `signalInventories` привязаны к material/version/hash и сохраняются в checkpoint после каждого полного документа. Повторный пакет сегментов использует тот же реестр. Извлечение ограничено шестью окнами и 4800 символами текста на запрос, максимум два независимых пакета одновременно. Каждое окно остаётся целиком; соседние 400 символов служат только контекстом продолжения. Проверка всех окон, точных цитат и host-generated IDs обязательна. Допускается только изменение пробельных символов цитаты: host восстанавливает исходный фрагмент; числа, пунктуация и OCR-написание не исправляются.

В сегментную фазу передаются реестр и исходные цитаты, без повторения полных оригиналов. У каждого signalId отдельный итог: used/merged с фактической ссылкой из вывода либо background/not_applicable/unreadable с причиной. Использованный соседний сигнал не закрывает пропуск. `coverageVersion=4` обязателен в текущем runtime; версии 2/3 читаются, но пересматриваются при продолжении задачи. Старое описание sourceCoverage ниже относится к прежнему протоколу и сохранено для объяснения миграции.

Сегменты строятся по полному известному ОКВЭД. 45.11 и 45.31 больше не объединяются в 45; наличие общего префикса не доказывает одинаковую экспозицию. Вывод сохраняет decisionQuestion, distinctContribution, priority и novelty. Это качественная оценка модели, не калиброванный рейтинг. Host отклоняет точные дубликаты по набору сигналов, сегментов и механизму; смысловые дубли пока проверяет модель.

При наличии собственных документов, без иных причин углубления, дешёвая отдельная фаза оценивает их связь с механизмами новости. Только полный набор явных unrelated с проверенными цитатами допускает applicability. Unknown, неполнота, превышение восьми документов/60000 символов сохраняют company_deep. Коррекции и source triggers по-прежнему требуют пересмотра. Предыдущие канонические вопросы фильтруются по механизмам, включая каналы сегментных сигналов; вопросы старого формата без типизированного механизма не отбрасываются.

Общий реестр ограничен 128 сигналами; фактически сериализованный сегментный вход — 120000 символами с резервом до 48000 результата, 10000 review-overhead и 2000 запаса в общем лимите 180000. Исходные оригиналы перед извлечением по-прежнему ограничены 90000 символами. Избыточные целые material/version bundles учитываются в omittedSources, retrievalExhaustive=false. Это явная неполнота, не доказательство отсутствия сигналов. Тайм-аут пакета автоматически повторяется максимум три раза; checkpoint готовых документов сохраняется.

Модель перечисляет signalIds внутри выводов и отдельные причины для оставшихся сигналов. Полный signalCoverage восстанавливает host, чтобы не дублировать все использованные ID в ответе. Отсутствующий и в выводах, и в причинах сигнал отклоняет результат; пометка used без ссылки не считается найденным выводом и нормализуется в background с явной причиной.

Если проверка выявила пропущенные строки, тот же инструмент принимает coveragePatch. Последний полный draft сохраняется в durable state до валидации; patch меняет только строки учёта и не меняет выводы. Полная валидация выполняется повторно, неполный draft никогда не становится принятым результатом. Для изменения вывода нужна полная замена плана. Контекст review содержит компактный draft без производных sourceRefs, sourceCoverage и индексов; их восстанавливает host из неизменного каталога. Резерв результата проверяется по этому фактическому контексту.

Контракт инструмента явно разделяет `{plan: полныйПлан, coveragePatch: null}` и `{plan: null, coveragePatch: строки}`. Противоречия между ссылками и исключениями возвращаются сразу полным списком с индексами. После шести неуспешных содержательных валидаций сегментная фаза завершается ошибкой без принятого результата; ошибки самой JSON-схемы до обработчика ограничиваются общим deadline фазы. Тайм-аут допускает ограниченный retry, ошибка контракта не запускает бесконечные повторы.

До появления полного draft schema требует ненулевой plan и не разрешает coveragePatch. queries по умолчанию пуст, segmentCoverage необязателен: host перечисляет все запрошенные сегменты и вычисляет связи из segmentKeys выводов. Отсутствие вывода получает механическую отметку отсутствия принятой связи, а не утверждение неприменимости. Модель по-прежнему обязана учесть каждый отдельный сигнал.

Review реестра выполняется точечно: для каждого unit проверяющий выбирает keep или replace. Keep сохраняет проверенные исходные signals/IDs/quotes; replace содержит полную замену ровно своего окна и проходит те же проверки цитат. Модель не обязана заново переписывать корректные цитаты. Это снижает повторную генерацию, но не гарантирует верную семантическую оценку периода или OCR.

## Идентичность вопроса

Канонический вопрос принадлежит компании и буквальному объекту; ключ включает mechanism, frame, unit, экономический targetPeriod, baselinePeriod и basis. Новость не входит в ключ вопроса: material/version и triggering source хранятся в ревизии и отдельной квитанции обработки.

У качественного event_only нет измеряемого экономического окна: host нормализует targetPeriod=unknown, baselinePeriod=null, basis=qualitative. Дата публикации остаётся у новости. Денежные absolute/budget_delta сохраняют собственные периоды и baseline; разные механизмы не склеиваются.

При переходе с прежнего датированного качественного ключа сохраняются effectId, история и previousRevisionId. Точное повторение ранее принятого запроса возвращает прежнюю квитанцию. Неоднозначное схождение нескольких историй требует явного разрешения, а не автоматического удаления. Ненормализуемая старая история остаётся читаемой и не блокирует другие механизмы.

## Применимость и публикация

Applicability хранит status (established/unknown/excluded), basis, explanation, точные sourceRefs и assumptions.

- `unknown`: собственная экспозиция/обязательные факты не установлены; publicationClass=`missing_data`, денежный расчёт, включая ноль, запрещён. Пропущенный Impact не обходит это правило.
- `conditional`: собственная экспозиция established, приведён собственный документ компании и явные assumptions сценария; publicationClass=`scenario`.
- `supported`: собственная экспозиция established; нет неизвестных обязательных посылок и assumptions; publicationClass=`consequence`.
- `unaffected` также требует документированного собственного основания; это не вывод из отсутствия документов.

Флаги provided-bank-csv и публичная макроаналитика не устанавливают долг, остаток, договорную формулу или роль. Host проверяет точную версию/хеш/компанию источника; семантическое соответствие cited document и утверждения по-прежнему требует обоснования модели и оценки качества. Само наличие company-документа не является автоматической верификацией его содержания.

## Бюджет контекста

ContextService по умолчанию ограничивает decoded JSON новости и оригиналов 120000 символами. Экранирование кириллицы не умножает расход на шесть; формат хеширования неизменяемых источников не меняется. Обязательные профили/явно запрошенные originals/версии новости сохраняются; необязательные группы версий одного materialId упаковываются целиком по retrieval rank. coverage.budget возвращает максимум, использованный размер, omittedSources и stopReason. Документы не обрезаются и не пересказываются вместо оригинала.

AgentService ограничивает полный proposal/review payload 160000 символами, учитывая предыдущие вопросы, черновики, arithmeticFeedback и каталоги. Это оставляет резерв относительно прежних 180000. При переполнении исключает целые необязательные группы; все company originals, cited draft sources, новость и trigger обязательны. Tool admission учитывает originals вместе с objectCatalog, накопленный размер фактических tool responses и повторные чтения. В ответе повторяются только refs уже известных оригиналов. Непоместившийся полный ответ не расширяет доступный модели каталог, фиксирует context_budget и сохраняет неизвестность.

Это измеримый бюджет символов, не точный tokenizer budget провайдера. Если сами обязательные оригиналы и assessment больше лимита, host возвращает явный bounded failure; автоматического разбиения произвольно большого обязательного дела на подзадачи пока нет.

## Уровни и фактическая глубина

Сохранены четыре уровня: общий/сегментный, группа, компания/объект, человек/роль. Group/person projections ссылаются на канонические последствия и проверенные membership/grants; не создают новые деньги или роли. Без подтверждённых групп/ролей эти уровни пусты.

Порядок: общий news planner один раз → candidate discovery → общий разбор сегментов → чтение предыдущего канонического состояния и SQL-инвентаря собственных документов (без оригиналов, embedding и rerank) → host выбирает глубину.

- `general`: собственного профиля/оригиналов нет; остаётся общий вывод и неизвестность применимости.
- `applicability`: есть только CSV-профиль; сохраняются квитанция оценки, решение глубины и ссылки на общие гипотезы, без company LLM, полного retrieval и фиктивного бизнес-вопроса.
- `company_deep`: есть собственный оригинал, предыдущее каноническое состояние, исправление новости, source trigger либо неполный инвентарь; выполняются retrieval → proposal → arithmetic preview → final review → атомарная запись. Наличие документа разрешает чтение, но не устанавливает финансовую экспозицию.
- `canonical_projection`: изменение подтверждённой группы/роли обновляет проекцию уже сохранённых последствий. Прямых LLM-разборов для каждой группы/персоны нет.

Сегментные гипотезы общие для новости; CSV-флаг не доказывает применимость конкретной компании. Решение содержит reason, sourceRefs, полноту инвентаря и missingFacts. Пустая квитанция имеет contextComplete=false и не означает нулевой эффект. Предыдущее состояние не пропускается ради экономии.

Первый собственный документ автоматически ставит компанию на пересмотр через durable source-change watch. До записи квитанции сохраняется курсор изменений из атомарного SQL-снимка; после записи догоняются события, включая появившиеся между snapshot и квитанцией, и уже известные события с knownAt>asOf. Follow-up сохраняется перед продвижением курсора. Scoped-изменения другой компании не инвалидируют чужие вопросы. Полнота относится только к загруженному корпусу, а не ко всем внешним документам.

## Тайм-ауты

Безопасные GET и явно перечисленные идемпотентные/читающие POST повторяются максимум 3 попытки с паузами 1 и 2 секунды и новым AbortSignal. Повторяются deadline и HTTP 408/504; ошибки валидации/ACL и CAS-записи lease/cursor не повторяются. Фаза модели при типизированном тайм-ауте провайдера/рантайма также получает максимум 3 попытки с новой беседой; предыдущая останавливается. HTTP-инструменты ограничены общим 180-секундным deadline фазы, без его продления. Повтор фазы может снова расходовать токены; попытки сохраняются в трассах/логах. Это ограниченное восстановление тайм-аутов, не бесконечный retry всех ошибок.

## Проверка

Автоматические тесты проверяют переход между независимыми новостями, разные денежные окна, rekey старой истории, replay, выбор глубины и retry.

## Общий разбор сегментов

После отбора компаний host объединяет их по двухзначному ОКВЭД из профиля; отсутствие распознаваемого кода отмечается в unsegmentedCompanyIds. Связь с сегментом — маршрут проверки, а не доказательство экспозиции. Отраслевые labels берутся из профиля, регион и индивидуальные финансовые признаки в сегментную модель не передаются.

Для каждого сегмента выполняется отдельный публичный поиск по отраслевым labels и теме новости. Оригиналы объединяются для пакета до 8 сегментов; модель выполняет proposal и отдельную сверку с оригиналами на пакет. Лимит 90000 символов входа и 16 оригиналов; версии одного материала допускаются/исключаются целиком. В записи сохраняются omittedSources и retrievalExhaustive. Это не обещание исчерпывающего поиска.

Сегментная модель получает полные допущенные публичные оригиналы. Каждый вывод обязан цитировать исходную новость и публичный оригинал. segmentCoverage содержит ровно одну запись на каждый входной сегмент: индексы выводов либо пустой массив и причину. Хост проверяет ключи, индексы, доступ, время и точные refs. Сегментные гипотезы сохраняются в checkpoint/result.segmentBatches; companyRun.segmentKeys связывает их с компаниями без копирования в канонические финансовые последствия.

Завершённые пакеты переживают продолжение/повтор задачи. Поздние компании того же сегмента получают связь без повторного LLM; новые нишевые labels требуют обновить пакет. Старые решения глубины действуют дальше: отраслевой риск сам по себе не запускает индивидуальный полный разбор и не делает unknown установленной экспозицией.

Сегментный reviewer получает исходные оригиналы и черновик, проверяет числа/единицы/периоды/базы сравнения и причинность. В обоих проходах result tool проверяет coverage и refs по каталогу host и возвращает ошибку модели для исправления в той же беседе; после завершения host повторно валидирует итог. Это модельная семантическая проверка, не доказательство безошибочности. Все попытки входят в traces/usage. Hydration ограничен 64 чтениями на пакет; заведомо не помещающиеся bundles не читаются.

## Проверка пропусков внутри источников

Полные оригиналы передаются как последовательные окна до 2400 символов без удаления текста. Host назначает unitId по material/version/hash и границам окна. Бюджет допускает до 64 окон на пакет; не помещающийся bundle исключается целиком с omittedSources. sourceCoverage сначала перечисляет обнаруженные в каждом окне факты, прогнозы, гипотезы и неизвестности в signals; затем обязан учесть каждое окно ровно один раз: used, background, not_applicable или unreadable с причиной. Host определяет used по фактическим связям. Если модель пометила used без связанного вывода, сохраняется background с явной причиной отсутствия связи и неизменным signals. Used ссылается на существующие выводы, цитирующие именно его оригинал; каждый вывод должен иметь такую поддержку. Проверка структуры не доказывает смысловую полноту или истинность интерпретации.

Proposal сначала рассматривает источники по каналам спроса, прибыли/денежных потоков, кредита, труда, предложения/логистики, валюты и пересмотра прогнозов. Reviewer независимо ищет пропуски, включая окна, уже отмеченные used. До 24 сегментных выводов на пакет позволяют сохранить несколько механизмов; у общего planner остаётся лимит 8. Новых company LLM-проходов это не добавляет. Модель выбирает sourceUnitIds и segmentKeys из enum-каталогов; точные sourceRefs и индексы связей строит host. Старые checkpoint-пакеты без coverageVersion=3 пересматриваются при продолжении задачи.

Перед принятием result tool проверяет сериализованный результат: не более 48000 символов и не больше остатка review-бюджета после полных оригиналов и резерва 10000 символов. При превышении модель получает запрос сократить формулировки без удаления строк coverage или механизмов. Оригиналы не обрезаются; общий предел этапа остаётся 180000 символов. Это символьный бюджет, а не точная токенизация.

Pipe-таблицы разбиваются на строки с точным tableHeader из оригинала; поддерживаются две и более колонок, с внешними pipes и без них. Текст восстанавливается конкатенацией units без потерь. Admission дополнительно проверяет фактический сериализованный размер units/headers/metadata в 90000 символов. Старые batches версии 2 читаются для совместимости, затем инвалидируются. Это учёт уже извлечённого текста таблицы, не PDF parser.

Сегментные proposal/review имеют host и Flue deadline 360 секунд. Остальные фазы — 180 секунд. Автоматические повторы остаются ограничены тремя попытками с новыми сигналами отмены; это не бесконечное продление.
